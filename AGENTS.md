# Working in this repository

## C# code style

**K&R bracing.** The opening brace stays on the declaration line, and `else`, `catch` and
`finally` stay on the line that closes the block before them.

```csharp
public sealed record SqlIndexColumn {
    [JsonPropertyName("name")]
    public required string Name { get; init; }
}

if (found) {
    Use(found);
} else {
    Fail();
}
```

This is set in [`.editorconfig`](.editorconfig) under `[*.cs]`, with
`dotnet_diagnostic.IDE0055.severity = error`. That severity, plus `EnforceCodeStyleInBuild` and
`TreatWarningsAsErrors` in `dotnet/Directory.Build.props`, means a formatting violation breaks the
build rather than merely showing up in a report.

```bash
npm run format:csharp:check   # dotnet format --verify-no-changes --severity error; CI runs this
npm run format:csharp         # fix it
```

⚠️ **`dotnet format` will not check a generated file.** A `// <auto-generated />` header makes it
skip the file entirely, so a generator emitting the wrong brace style diverges silently — which is
exactly what happened in the sibling `cli-schema` repository once. The emitter in
[`scripts/emit-csharp.mjs`](scripts/emit-csharp.mjs) produces K&R deliberately; keep it that way
rather than relying on the formatter to notice.

## Generated code

**Do not hand-edit `packages/sql-schema/src/generated/` or
`dotnet/src/CairnTool.SqlSchema/Generated/`.** Both are produced from
[`spec/v1/sql-schema.json`](spec/v1/sql-schema.json); an edit is overwritten by the next run and
rejected by CI.

```bash
npm run codegen        # regenerate both languages
npm run codegen:check  # CI gate
```

The emitter constrains what the schema may contain. Three rules, each of which produces C# that
does not compile — or that silently deserializes wrong — when broken:

- **No `oneOf` / `anyOf` anywhere.** `typeOf` has no branch for them and falls through to `object`.
  This is why the document has one array per object kind rather than a single `objects[]`
  discriminated by `kind`.
- **There is no 64-bit integer.** `"integer"` becomes `int`. Any SQL value that can exceed int32 —
  an identity seed on a `BIGINT`, a sequence bound — is a **string** carrying the literal.
- **`additionalProperties` holding an inline object is broken.** `typeOf` names a type for it but
  `collect` never walks into `additionalProperties`, so the type is never emitted. A dictionary
  value must be a `$ref` to a `$defs` entry, or free-form (`true`) — which is what the `extensions`
  bag uses.

Every object node in the schema carries an explicit `title`, because an untitled inline object is
named `Owner + PascalCase(property)` and those collide. A `$ref` must not carry sibling keys: they
are legal in 2020-12 and they apply, so the TypeScript generator forks a renamed duplicate type
while the C# emitter ignores them — and the two languages stop agreeing on type names. Put the
prose on the definition being referenced instead. `npm run spec:lint` enforces all of this.

### The C# style gate lives in the generator

`scripts/emit-csharp.mjs` is byte-identical to the copies in the `cli-schema` and `kps-docs`
repositories, and is kept that way. It indents every type by four spaces, which is correct for a
block-scoped namespace — but it emits a **file-scoped** one, under which a type belongs at column
zero. `scripts/codegen.mjs` corrects that on the way out rather than forking the emitter, and then
asserts the result is K&R braced and correctly indented before writing it.

That assertion is not belt-and-braces. Because `dotnet format` and the IDE analyzers both skip
`// <auto-generated />` files, **the generator is the only thing that can enforce style on this
output** — `npm run format:csharp:check` cannot see it at all.

> Both sibling repositories have the same four-space offset in their committed generated C# today.
> Neither has noticed, for exactly this reason.

## The fixtures

`spec/fixtures/` holds `.sql` sources and a `.sqlproj` per case. **The `.dacpac` they produce is
not committed**: a dacpac is a zip whose `Origin.xml` carries checksums and a build timestamp, so
it is not byte-reproducible, and its diff is an opaque binary blob no reviewer can read. The `.sql`
is the reviewable artifact — "we added a computed column" is a one-line diff there and nothing at
all in a dacpac. `npm run fixtures` rebuilds them into `artifacts/fixtures/`.

**`spec/fixtures/legacy/legacy.dacpac` is the one exception**, and it is negated explicitly in
[`.gitignore`](.gitignore). It is frozen: produced once by the `Microsoft.Build.Sql`
0.1.12-preview toolchain and **never regenerated**. It proves the one thing source-built fixtures
cannot — that today's extractor still reads a dacpac built by a toolchain we no longer run.
Regenerating it destroys the only backward-compatibility evidence in the repository.

⚠️ **`spec/fixtures/global.json` pins the .NET SDK to 8.x, and it is scoped to that directory on
purpose.** `Microsoft.Build.Sql` 0.1.12-preview is what the consuming estate uses, and the estate
pins SDK 8.0.407. The repository root deliberately has **no** `global.json`, so the TypeScript and
C# build stays on SDK 10. Adding one at the root breaks the rest of the repository.

## DacFx and MSBuild

⚠️ **The MSBuild integration never loads DacFx into the MSBuild process. Any pull request that adds
a `UsingTask` to this repository is wrong.**

`Microsoft.Build.Sql` 0.1.12-preview ships its own DacFx at
`tools/netstandard2.1/Microsoft.SqlServer.Dac.dll` — file version **162.1.124.2**, assembly version
**17.0.0.0**. The DacFx this repository depends on, 170.5.96, has the **same assembly version
17.0.0.0**. Same identity, eight major file versions apart. The loader has no basis on which to
prefer ours and no error to report when it picks theirs, and which one an in-process task binds to
depends on target execution order — which is not stable across incremental versus clean, `-m`
versus single-proc, or IDE versus CLI.

It is also architecture-dependent. `Microsoft.Data.Tools.Schema.SqlTasks.targets` sets
`UseTaskHostFactory` to true only when `ProcessArchitecture` is not `Arm`/`Arm64`. On x64 the SDK's
own tasks go out-of-process and DacFx 162 never enters the MSBuild node; on Apple Silicon it does.
An in-process design passes on `ubuntu-latest` and fails on every developer's M-series laptop.

`CairnTool.SqlSchema.MSBuild` therefore `Exec`s the tool as a separate process. That is the whole
reason the package carries the tool's publish closure under `tasks/` instead of a task assembly.

## These packages are published

One npm package and four NuGet packages, all on one version number. **A change to a generated type
is a change to somebody else's compile.** A type that is merely shaped differently — a class where
there was a record, a `List` where there was an `IReadOnlyList`, an init property where there was a
constructor parameter — is still breaking.

The conformance goldens are the instrument for catching it:

```bash
npm run fixtures
npm run build && npm test
dotnet test dotnet/SqlSchema.slnx -c Release
npm run conformance && npm run coverage
```

**The gate is that every golden still matches with no `expected.json` edited.** A golden that needs
changing means the wire format moved, which is a bug in the change rather than an intended outcome.
`git diff spec/conformance/` must come back empty.

## Releasing

semantic-release, off a green CI run on `main`. The commit subjects decide the version, which is
why commitlint is a gate: a commit that does not parse produces no release.

**One version number across all five packages**, computed once and passed to `dotnet pack` on the
command line. That is what makes the npm package and the four NuGet packages incapable of drifting
apart. There is no `<Version>` anywhere in `dotnet/`, deliberately.

Neither registry has a stored credential. Both use OIDC trusted publishing, and the policies are
bound to this repository **and to `release.yml` by filename** — renaming that file breaks
publishing. Only `RELEASE_APP_ID` and `RELEASE_APP_PRIVATE_KEY` exist, for the App whose
installation token authenticates the tag, the changelog commit and the release.

⚠️ **The first npm publish needs a one-off token.** npm only lets a trusted publisher be
configured on a package that already exists, so `@cairn-tool/sql-schema` cannot use OIDC until it
has been published once. Add `NPM_TOKEN`, release, register the trusted publisher on npmjs.com,
then delete the secret. nuget.org has no such bootstrap: its policy admits new package IDs, so all
four NuGet packages publish on OIDC from the first release.

The MSBuild package carries the tool as its payload, and its pack step forwards `-p:Version` to the
publish that produces it. Without that the payload would be built at the default 1.0.0 while the
package carried the real version, and every document written through MSBuild would report the
wrong `tool.version`.

## The spec

[`spec/README.md`](spec/README.md) is normative. `schemaVersion` is hand-owned and independent of
the package versions. No schema sets `additionalProperties: false`, so adding a property is
non-breaking and consumers must ignore what they do not recognise. Adding a definition is additive;
adding a `required` entry is not, and belongs in `spec/README.md` where a reader will find it.

**The core is engine-neutral; SQL Server is the only engine implemented.** A member belongs in the
core only if it exists, and means the same thing, in at least two of {SQL Server, PostgreSQL,
MySQL, Oracle}. Everything else goes in the per-engine `extensions` bag, and is promoted only when
a _second_ engine implementation needs it — never speculatively.
